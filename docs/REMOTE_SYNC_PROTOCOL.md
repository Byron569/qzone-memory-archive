# 双端协作恢复：远程同步协议草案

本文定义“双方各自发现记录、服务端暂存、另一端下次刷新时补齐”的可插拔协议。它是客户端与未来远程服务之间的契约，不代表当前版本已经部署了公网服务。

当前客户端仍应优先支持本地证据包导出/导入。远程 provider 只是同一套数据模型的另一种传输方式，这样可以先验证匹配规则，再决定是否长期维护服务器。

## 目标与边界

协议解决的是“双方账号各自拥有部分记录”的同步问题：

1. A、B 在各自设备上完成本地归档。
2. 双方用一次性配对码建立一个同步关系。
3. 某一方发现自己拥有、另一方暂时缺失的互动证据，就生成变更并加密上传。
4. 另一方刷新时按游标拉取、解密、校验，并将候选记录放入本地恢复队列。
5. 只有本地匹配规则确认后，记录才进入归档数据库；远程数据不能直接覆盖本地归档。

协议不负责也不允许以下事情：

- 上传 QQ Cookie、`g_tk`、User-Agent、密码、二维码登录票据或任何可恢复会话的字段；
- 让服务器代替客户端访问 QQ 空间；
- 绕过权限、验证码、风控、删除限制或恢复未经授权的账号内容；
- 在没有用户确认的情况下，把对方内容写入本地正式归档；
- 以公网 IP 为前提。远程 provider 可以部署在 HTTPS Serverless、托管 API 或 VPS 上，本地 provider 不需要公网服务。

## 配对流程

配对码是短期、一次性、只能使用一次的邀请，不是账号密码：

1. A 客户端生成随机 `pairingId`、短期 `code` 和临时密钥对。二维码只携带 `pairingId + code + A 的公钥`。
2. A 将二维码或代码展示给 B。服务端只保存配对码的慢哈希、过期时间和尝试次数，不保存明文代码。
3. B 扫描后提交 `pairingId + code + B 的公钥`。校验成功后服务端把双方设备标记为 `paired`，并返回双方都能验证的会话信息。
4. 双方客户端通过密钥协商得到配对密钥。配对私钥只保留在各自系统的安全存储中，不能进入 SQLite、前端持久化、日志或同步包。
5. 任一方可撤销配对。撤销后服务端拒绝新的上传和拉取；客户端仍可保留已经下载的本地证据，是否删除由用户明确决定。

建议的限制：配对码有效期 10 分钟、单次使用、连续失败后退避；配对会话默认 30 天无活动过期。具体时长属于服务端配置，不应写死在客户端业务逻辑中。

`RecoveryPairingCode`、`RecoveryPairingSession` 和 `RecoveryDeviceIdentity` 位于 `src/utils/recoverySync.ts`。

## 端到端加密

服务器只能看到最小化的同步元数据：配对会话标识、不可逆记录标识、版本号、时间、操作类型和密文长度。说说正文、昵称、QQ 号、图片/视频信息、原始 JSON 等全部放在密文中。

每一条变更使用以下逻辑：

- 客户端用配对密钥加密明文 `RecoveryEvidenceRecord`；
- 每条变更使用唯一随机 nonce；
- AAD 至少绑定 `protocolVersion + pairId + recordId + revision + operation`，防止密文被挪到另一条记录；
- 服务器保存 `ciphertextB64`、`nonceB64`、可选 `aadB64`、密文摘要和版本，不拥有解密密钥；
- 客户端解密后仍要做 schema 校验、大小限制、记录指纹校验和账号授权校验。

实现阶段可以使用平台提供的成熟 AEAD/密钥协商库，但不能自行设计加密算法。协议文件和 TypeScript 类型只定义字段，不代表已经完成密码学实现。

## 变更与游标同步

同步采用“追加变更流 + 客户端游标”，而不是每次全量比较：

- `upsert`：新增或补充一条证据；
- `tombstone`：表示用户要求删除这条远程证据；它不是立即物理删除；
- `revision`：同一 `recordId` 的单调递增版本；
- `changedAt`：服务端排序和审计时间；
- `RecoverySyncCursor`：包含 `streamId + position + issuedAt`，客户端成功处理后才确认游标。

推荐顺序：

1. 客户端读取本地待上传变更，按 `recordId/revision` 去重。
2. `pushChanges` 上传密文；服务端返回接受数、拒绝数、冲突和下一游标。
3. 客户端从上次已确认游标调用 `pullChanges`，限制单页数量（当前类型提供 1～500 的边界）。
4. 每条密文完成解密、验证、落地本地恢复候选队列后，客户端才调用 `acknowledgeChanges`。
5. 拉取中断时不要推进本地游标；重试必须能够安全幂等。

游标不是权限凭证，不能单独用于访问其他配对关系。服务端应将游标绑定到配对会话和设备，并拒绝倒退或跨会话使用。

## 本地匹配、冲突和合并

服务端不做 QQ 内容语义判断。客户端用以下优先级生成稳定 `recordId`：

1. QQ 的稳定 `feedKey/cellId`；
2. 原始作者、事件时间、事件类型和内容摘要的规范化组合；
3. 媒体指纹作为辅助，不能单独作为唯一键。

收到证据后，先进入“待确认恢复”状态。只有以下检查全部通过才可合并：

- 目标账号是当前用户拥有或明确授权的账号；
- 证据的来源侧确实是已配对的另一端；
- 记录指纹与本地缺失项匹配，且不是已删除或已拒绝项；
- 图片/视频数量、作者、时间等关键字段没有明显冲突。

冲突策略分四类：

- `prefer-local`：本地已经确认的字段优先，适合只补缺失媒体；
- `prefer-remote`：仅适用于用户明确选择的字段，不应默认使用；
- `keep-both`：保留两个候选并标记来源，适合正文或作者不一致；
- `manual`：进入人工确认队列，默认策略。

任何“自动合并”都只能补齐明确缺失字段，不能静默覆盖用户已经归档的正文、作者、时间或媒体。冲突结果应保留双方摘要、版本和来源，方便审计与撤销。

## 删除、撤销和保留期

删除分三层处理：

1. 用户在本地删除：本地标记删除并生成 `tombstone`，不立即从服务器物理删除。
2. 服务端删除：配对双方都确认收到 tombstone 后，经过短暂保留期再清理密文；备份中的删除遵循同样的生命周期。
3. 正式归档删除：仅删除本地归档，不反向删除对方设备的原始归档，除非用户明确对两端都执行删除。

撤销配对会停止同步，但不会自动删除已经下载的证据。设置页应提供单独的“删除远程副本”“删除本地证据”“撤销配对”操作，并明确提示影响范围。

## 服务端最小接口建议

远程实现可以围绕 `RecoverySyncProvider` 提供以下 HTTPS API：

- `POST /pairings`：创建一次性配对码；
- `POST /pairings/{id}/accept`：提交代码并完成配对；
- `POST /pairings/{id}/revoke`：撤销配对；
- `POST /sync/{id}/changes`：幂等上传加密变更；
- `GET /sync/{id}/changes?cursor=...&limit=...`：按游标拉取；
- `POST /sync/{id}/ack`：确认已安全落地的游标；
- `DELETE /sync/{id}/device`：删除设备与待清理密文。

服务端必须具备鉴权、限流、重放保护、大小限制、审计日志和备份删除策略。日志中不得记录请求体、配对明文代码、密文解密结果或任何 QQ 登录信息。

## 分阶段落地建议

1. **本地协议阶段**：先实现 JSON 证据包 provider，测试 `recordId`、游标、幂等和冲突展示；不需要服务器。
2. **抽象接入阶段**：归档引擎只依赖 `RecoverySyncProvider`，本地文件和 HTTPS provider 可互换。
3. **小范围远程试运行**：部署最小 HTTPS API，只开放配对、加密变更和游标；默认关闭媒体原文件上传。
4. **正式服务阶段**：补齐账户删除、备份清理、限流、监控、费用和服务条款后，再考虑图片/视频对象存储。

公网 IP 不是第一阶段的必要条件。真正需要先解决的是客户端加密、授权边界、幂等同步和删除语义；这些稳定后，后端可以替换而不影响本地恢复逻辑。
